# Design

## Context

동기·범위는 [proposal.md](proposal.md)에 둔다. 구현 계약은 [내보내기](specs/schedule-export/spec.md), [알림 안내](specs/calendar-reminder/spec.md), [사용 지표](specs/usage-analytics/spec.md)다. 이 문서의 명령과 검증은 **구현 단계에서 수행할 절차**이며, 이번 명세 작성에서 수행했다고 뜻하지 않는다.

2026-10-26 확인한 상태:

- 라이브는 v1.3 `20261021-27`. 소스는 React 18·TypeScript·Vite, 패키지 선언의 SDK는 3.7.0, Devtools는 `^3.7.0`이고 실제 설치본은 3.8.0이다.
- 패턴 저장 성공 위치는 `App.tsx`의 `savePattern`에서 `saveSettings`가 끝난 뒤다. 이력 불러오기만 하는 동작은 저장 성공이 아니다.
- 내보내기는 `CalendarScreen.tsx`의 `runExport` → `exportMonth`이며 결과는 `opened|failed|unsupported`이다. 공유 취소를 별도로 식별하지 못한다.
- `ExportSheet.tsx`의 알림 꺼짐 안내와 `CalendarReminderScreen.tsx`의 기본 알림 주의 문구가 다르다. `buildIcs`의 같은 UID는 외부 캘린더 앱의 갱신 동작을 보장하지 않는다.
- 현재 저장 형식은 `turncal.settings` v3·`turncal.entries` v1이며, 새 분석 이벤트는 없다. 기존 SDK에도 `Analytics.log`·`Analytics.click`이 실제 선언되어 있다.
- 공식 npm의 SDK 3.9.0 타입과 Devtools 3.9.0 mock을 임시로 읽어 위 분석 API의 존재를 확인했다. Node는 24.21.0이고 Devtools 3.9.0의 Node >=24 조건을 충족한다. 프로젝트 설치·컴파일·실기기 호환은 아직 확인하지 않았다.
- 핵심 지표·평점·문의 MCP는 서버가 “등록되지 않은 요청”으로 거부했다. 콘솔의 현재 핵심 지표를 미설정으로 간주하지 않는다.
- 직전 분석의 기준선은 타입 검사 통과·3개 시간대 단위 테스트 각 367개 통과다. 새 구현의 검증 결과로 재사용하지 않는다.

## Goals / Non-Goals

**Goals:**
- 문구와 파일 생성·가져오기·알림의 책임을 일치시킨다.
- 저장 성공·내보내기 시도·SDK 반환을 작은 이벤트 계약으로 구별한다.
- SDK 교체와 기능 변경의 실패 원인을 구분할 수 있도록 단계별 검증한다.

**Non-Goals:**
- 자체 푸시, 서버, 로그인, 동기화, 백업/복원, 외부 캘린더 직접 수정.
- React·TDS·Vite·TypeScript·npm의 동반 업그레이드, 광고 유형·권한 변경.
- 일반 분석 프레임워크, 이벤트 재전송 큐, 분석 실패 UI, 과거 데이터의 소급 수집.
- 기존 일정을 자동 삭제·수정하거나 재가져오기를 모든 앱에서 같게 만드는 처리.

## Decisions

### 1. 알림 문구만 바꾸고 생성 규칙은 유지

`ExportSheet.tsx`에서 현재 시각을 넣은 상태 문장과 공통 주의 문장을 별도 텍스트로 표시한다. 실기기에서 시트 안의 글자가 너무 작다는 사용자 의견(2026-10-27)에 따라, 아래 "내보내기" 문구는 "캘린더 파일 보내기"를 고른 뒤 뜨는 TDS `ConfirmDialog`(제목 "캘린더 파일을 보낼까요?", [취소]/[보내기])에 보여 준다. [보내기]를 눌러야 공유 창을 연다.

| 위치·상태 | 문구 |
|---|---|
| 내보내기·켜짐 | 근무 전날 HH:00 알림을 파일에 넣어요. 비번·휴무는 제외해요. |
| 내보내기·꺼짐 | 턴캘 알림을 파일에 넣지 않아요. 설정에서 켤 수 있어요. |
| 내보내기·공통 | 캘린더 앱의 기본 알림이 따로 붙을 수 있어요. |
| 내보내기·재가져오기 | 이미 가져온 달은 그 달 일정을 지운 뒤 가져와야 바뀌어요. 저장된 캘린더는 가져온 뒤 확인해 주세요. |
| 알림 설정·재가져오기 | 설정을 바꿔도 이미 추가한 일정은 자동으로 바뀌지 않아요. 다시 가져와도 기존 일정은 그대로라서, 그 달 일정을 지운 뒤 가져와 주세요. |

재가져오기 문구는 Galaxy S26 Ultra 실기기 실험(2026-10-27, `docs/ics-experiments/README.md`)을 근거로 한다. 이미 있는 UID는 갱신되지 않고 새 UID만 추가되며, 지운 뒤에는 다시 가져올 수 있다. 저장 캘린더는 파일로 정할 수 없고 기기 상태에 따라 달라진다.

알림 대상 4종·비번/휴무 제외·18~23시·기본 21시·VALARM·UID·파일 이름은 유지한다. 줄 수를 고정하거나 글자를 줄여 맞추지 않고 기존 스타일의 자연스러운 줄바꿈을 사용한다. 별도 문구 관리 계층은 만들지 않는다.

외부 일정의 자동 갱신을 구현하는 대안은 캘린더별 차이와 추가 권한·서버를 요구하므로 채택하지 않는다. 불일치가 실제로 발견되면 파일 내용 오류와 외부 앱의 가져오기 정책을 구분한다.

### 1-1. 내보내기 뒤 리뷰 요청 안내

사용자 결정(2026-10-27)으로, 내보내기 결과가 `opened`면 달력 하단에 "턴캘이 도움이 됐다면 리뷰를 남겨 주세요."와 [리뷰 남기기]를 보여 준다. 버튼을 누를 때만 `requestReview`를 호출한다(`src/platform/review.ts`). 공식 가이드에 따라 같은 실행에서 한 번만 요청하고, 결과를 기다리거나 노출 여부에 흐름을 의존하지 않으며, 미지원·예외는 무시한다. 공유 창은 취소해도 `opened`이므로 안내 글에 완료 표현을 넣지 않는다. 버튼을 눌러도 피로도 정책 때문에 리뷰 창이 뜨지 않을 수 있다(알려진 한계).

### 2. 최소 분석 모듈과 세 이벤트

`src/platform/analytics.ts`에 고정된 세 행동만 다루는 작은 함수를 둔다. 외부에 자유로운 속성 객체를 받는 범용 전송기는 공개하지 않는다.

| 이벤트 | SDK 호출 | 앱이 추가하는 속성 | 기록 위치 |
|---|---|---|---|
| `turncal_pattern_saved` | `Analytics.log`, `log_type=event` | 없음(`params={}`) | `App.savePattern`의 저장 성공 뒤, 화면 전환 전 |
| `turncal_export_requested` | `Analytics.click` | `format=image|calendar` | `runExport`가 선택을 받아 처리를 시작한 때 |
| `turncal_export_result` | `Analytics.log`, `log_type=event` | `format=image|calendar`, `result=opened|failed|unsupported` | `exportMonth` 결과가 반환된 뒤 |

`Analytics.log`의 인자는 `{ log_name, log_type, params }`, `Analytics.click`은 `{ log_name, format }`이다. `eventLog` 같은 deprecated 별칭이나 존재하지 않는 임의 이벤트 API는 쓰지 않는다. 세부 패턴, 날짜, 이름, 메모, 파일명, 원시 오류, 저장된 식별키는 읽거나 넣지 않는다. SDK가 기본으로 붙이는 `anonymous_key` 등은 자체 추가 속성과 구분하며 수집이 완전히 익명이라고 설명하지 않는다.

호출은 업무 흐름에서 직접 하며 `useEffect`·재렌더링·저장값 로딩에 연결하지 않는다. 함수는 전송을 기다리지 않고 동기 예외와 Promise 거부를 내부에서 처리한다. 반환되지 않는 분석 Promise도 업무를 막지 않아야 한다. 자체 타임아웃·큐·재시도·저장은 두지 않는다. 미지원으로 분석 함수가 없을 때도 업무는 계속한다.

분석 실패를 패턴 저장 실패나 내보내기 실패로 바꾸지 않는다. 기존 `busy` 제어와 실패 안내는 유지한다. 공유 취소를 알아낼 수 없으므로 `opened`를 `completed`로 바꾸거나 취소 이벤트를 새로 만들지 않는다.

### 3. 콘솔 지표는 코드 전송과 별도로 확인

| 구분 | 준비할 연결안 | 의미와 적용 조건 |
|---|---|---|
| 활성 | 기존 값 확인 후 제공되는 재방문 템플릿 검토 | 현행 값·실제 템플릿 확인 전 임의 교체하지 않음 |
| 대표 전환 후보 | 이름 “근무 패턴 저장”; `turncal_pattern_saved` | 저장 성공 이벤트가 발생한 사용자. “최초 등록”만의 지표로 부르지 않음 |
| 보조 전환 후보 | 이름 “근무표 공유 요청 반환”; `turncal_export_result`, `result=opened` | 공유 SDK 요청 반환 사용자. 파일 전송·저장 완료 지표가 아님 |

기존 지표 이름·대표 여부·조건을 콘솔 웹에서 확인한 뒤 비교안을 제시한다. 사용자가 확인한 변경만 등록한다. 기존 설정을 읽을 수 없으면 현 상태를 미확인으로 보존하고 코드 검증과 콘솔 설정 완료를 분리한다. 템플릿명·기간·계수를 확인 없이 만들어 등록하지 않는다.

SDK 로그는 개발/mock·QR에서 운영 분석에 집계되지 않을 수 있으므로 `window.__ait.state.analyticsLog`로 전송 계약을 검사한다. 운영 집계는 실제 출시 뒤 의미를 아는 테스트 행동을 수행하고 다음 날 이후 콘솔 “분석 > 이벤트”와 “핵심 지표”에서 확인한다. 즉시 나타나지 않는다고 0명이나 전송 실패로 결론내리지 않는다.

사용자가 입력한 근무표·메모가 기기에 저장된다는 설명은 유지하되, README·운영 설명에 “모든 데이터가 외부로 나가지 않는다”는 광범위한 표현이 있으면 본 변경의 SDK 행동 분석과 모순되지 않게 구분한다. 별도 동의 화면이나 권한을 임의 추가하지 않는다.

### 4. SDK 업데이트 준비

| 패키지·환경 | 현재 확인 | 목표 |
|---|---|---|
| `@apps-in-toss/web-framework` | 선언·설치 3.7.0 | 3.9.0 정확한 버전 고정 |
| `@apps-in-toss/devtools` | 선언 `^3.7.0`, 설치 3.8.0 | 3.9.0 정확한 버전 고정(devDependency) |
| SDK 내부 CLI | 3.7.0 의존 | SDK 3.9.0이 의존하는 CLI 3.9.0, 별도 중복 설치 안 함 |
| Node | 24.21.0 | 유지(Devtools 요구 >=24 충족) |
| React·TDS·Vite·TypeScript | 기존 lockfile 값 | 이 업데이트에서 변경하지 않음 |

공식 릴리스 노트의 3.9.0 변경은 IAP 중심이므로 이번 앱이 겪은 캘린더 오류의 수정 근거로 사용하지 않는다. 3.x 내 업데이트로 정하고 무분별한 `latest` 설치·`npm update`는 하지 않는다.

구현 단계의 의존성 변경 명령(이번 명세 작성에서는 실행하지 않음):

```powershell
npm install --save-exact @apps-in-toss/web-framework@3.9.0
npm install --save-dev --save-exact @apps-in-toss/devtools@3.9.0
npm ls @apps-in-toss/web-framework @apps-in-toss/devtools @apps-in-toss/cli
```

새 API 코드를 쓰기 전에 위 **의존성 변경만** 적용해 타입 검사·시간대별 단위 테스트를 실행한다. 패키지 선언·lockfile을 함께 관리하고 SDK/Devtools 및 필요한 전이 의존성 외의 변경은 검토한다. `npm ci`로 재현 가능성도 확인한다.

현재 사용 API의 회귀 확인:

| 영역 | 실제 호출 | 확인 기준 |
|---|---|---|
| 저장·식별 | `Storage.getItem/setItem/removeItem`, `User.getAnonymousKey` | 기존 저장값 읽기·보존, 초기화, 식별키 실패 격리 |
| 파일·공유 | `saveBase64Data.isSupported`, `saveBase64Data`, `Share.createLink` | 이미지/ICS, 두 번 내보내기, 취소, 실패·미지원·링크 타임아웃 |
| 화면·내비게이션 | `SafeArea`, `partner`, `tdsEvent`, `graniteEvent`, `closeView` | 안전 영역, 달력 설정 버튼, 뒤로가기 계층·종료 |
| 광고 | `TossAds`, `isMinVersionSupported` | 초기화, 배너 부착/해제, 광고 없음·오류 때 레이아웃 |
| 분석 | `Analytics.log/click` | 3.9.0 타입·mock에서 확인한 API, 실제 빌드·실행 검증은 구현 단계 |

### 5. 캘린더 실기기 검증 표

삼성 캘린더·구글 캘린더·iOS 캘린더 각각 아래 표를 수행한다. 기기/OS/토스/캘린더 앱 버전, 번들 ID, 테스트 날짜·시간대, 알림 권한·기본 알림 설정을 함께 기록한다. 삼성 기기의 기본 앱 이름을 추정해 쓰지 않고 실제 앱 정보를 확인한다.

테스트는 기존 개인 일정과 분리한 테스트 캘린더에서 한다. 테스트 달은 미래 날짜를 포함하는 달로 고르고 주간·오후·야간·당직·비번·휴무와 하루의 근무 변경을 포함한다. 기존 개인 일정 삭제나 캘린더 앱 설정 변경을 자동 수행하지 않는다.

| 사례 | 확인 내용 | 결과 기록 기준 |
|---|---|---|
| C01 최초 가져오기·켜짐 | 파일 일정 수·날짜·제목, 대상 4종의 21시 알림, 비번·휴무 | 파일 VALARM과 캘린더 앱이 추가한 기본 알림을 구분 |
| C02 같은 파일 재가져오기 | 동일 파일을 두 번 가져옴 | 일정 수와 중복/갱신/거부를 실제 결과로 기록 |
| C03 변경 파일 재가져오기 | 하루 근무 변경 후 새 파일 가져옴 | 같은 UID 유지, 변경 적용 여부와 중복 수 기록 |
| C04 시각 변경·꺼짐 | 21→20시 변경 파일, 토글 끈 파일을 각각 가져옴 | 파일 트리거/VALARM 0 확인, 외부 앱 기본 알림은 별도 기록 |
| C05 공유 반복·취소 | 같은 달 두 번 보내기, 공유 취소, 미지원·오류 | 파일명 충돌 없음, 거짓 완료 안내·취소 이벤트 없음 |
| C06 알림 실제 실행 | 미래의 대상 일정 한 건, 권한/시간대/외부 앱 설정 확인 | 일정에 알림 값이 있는 것과 실제 알림 도착을 별도 결과로 기록 |

결과 칸은 “미실행/확인/차이 있음/실패”와 증거로 남긴다. 지원되는 외부 앱의 가져오기 차이를 파일 오류로 단정하지 않는다. 파일 자체가 잘못되면 최소 수정 후 자동·동일 기기 재검증을 한다. 외부 앱별 차이라면 이 change의 안내 범위 안에서 설명하고, 자동 동기화·외부 일정 삭제를 추가하지 않는다. 기기가 없으면 해당 환경을 미실행으로 남기며 전체 호환 검증 완료라고 말하지 않는다.

## Risks / Trade-offs

- [SDK 변경과 새 분석의 원인 혼동] → 의존성만 먼저 검사하고, 이후 안내·분석을 붙여 통합 검사한다.
- [분석 Promise 거부로 저장 실패처럼 보임] → 업무 Promise와 분리하고 예외·거부·지연 검사를 추가한다.
- [중복 이벤트로 전환 과대 집계] → 성공 경로 직접 호출, 재렌더·실패·시트 닫기 검사, 자체 재시도 없음.
- [공유 취소가 전환처럼 보임] → 이름을 “공유 요청 반환”으로 제한하고 실제 전달 성과로 해석하지 않는다.
- [SDK 기본 식별 속성 누락 설명] → 앱 추가 속성과 SDK 자동 공통 속성을 구분한다.
- [캘린더가 중복 일정·기본 알림 추가] → 앱별 결과를 기록하고 반영·무알림을 보장하지 않는다.
- [로컬 main이 원격보다 문서 1커밋 뒤] → 기존 문서를 이번 계획에서 수정하지 않는다. 구현 시작 시 승인된 브랜치 정책에 맞춰 원격 최신을 포함하고 문서의 사용자 변경을 보존한다.

## Migration Plan

1. 저장 형식은 변경하지 않는다. 업데이트 전 v3 설정·이력·사용자 정의·알림·v1 세부 내용의 복원 검사를 새 SDK에서 유지한다.
2. SDK만 업데이트한 뒤 자동 검사를 통과시키고, 안내·분석 변경과 각 검사를 순서대로 적용한다. 단위 로직이 바뀌지 않는 문구는 별도 구현 복제 테스트 대신 관련 E2E로 확인한다.
3. `npm run typecheck`, `npm run test:tz`, 기존 E2E 14종과 새 분석 E2E, `npm run build:adtest`를 확인한다. 새 `.ait`를 올려 실기기에서 SDK 회귀와 C01~C06을 수행한다. 업로드·테스트 푸시는 별도 실행 요청 범위에 맞춰 진행한다.
4. 검증 후 출시용 빌드에서는 실제 광고 ID만 있는지, Devtools·mock·테스트 광고 ID·진단 코드가 없는지 확인한다. API 상수 이름이나 소스맵 문자열만으로 비밀 유출을 단정하지 않고 실제 값·실행 코드 포함 여부를 구분한다. 실제 ID 값은 문서·로그에 복사하지 않는다.
5. 검수 신청·출시는 사용자가 요청할 때만 진행한다. 현재 라이브 v1.3 `20261021-27`은 유지한다. 출시 후 실제 행동 이벤트와 지표 집계 확인은 아래 Workflow follow-up으로 분리한다.
6. 개발 중 문제가 나면 이번 SDK/Devtools 변경에 해당하는 선언·lockfile만 이전 값으로 되돌려 재설치·재검증한다. 사용자 변경을 덮어쓰지 않는다. 출시 후 되돌리기는 사용자가 대상을 확인해 요청할 때 기존 라이브 v1.3을 기준으로 검토한다. 재내보내기 오류가 있었던 v1.2를 기본 복귀 대상으로 삼지 않는다.

# Proposal

## Why

v1.3 출시 후 확인한 내보내기의 “알림 없이 보내요” 문구는 캘린더 앱이 붙이는 기본 알림과 혼동될 수 있고, 재가져오기 동작은 캘린더 앱별 확인이 부족하다. 2026-10-22 노출 정책에 맞춰 핵심 행동을 측정하면서 SDK 3.9.0으로 올릴 준비를 함께 한다.

## What Changes

- **요청 1 — 알림 안내:** 내보내기와 설정에서 “파일에 넣는 턴캘 알림”과 “캘린더 앱의 기본 알림”을 구분한다. 알림이 울리지 않는다고 보장하거나 파일을 다시 가져오면 기존 일정이 반드시 갱신된다고 안내하지 않는다.
- **요청 2 — 실기기 호환성:** 삼성 캘린더·구글 캘린더·iOS 캘린더에서 최초 가져오기, 같은 파일 재가져오기, 근무·알림 변경 뒤 재가져오기, 알림 켜기/끄기·비번/휴무를 확인할 시나리오와 결과 기록 기준을 정한다. 미확인 환경은 미확인으로 남긴다.
- **요청 3 — 핵심 지표:** 근무 패턴 저장, 내보내기 요청, 내보내기 SDK 결과의 세 이벤트를 추가한다. 저장 실패·재렌더링으로 성공 이벤트가 생기지 않으며, 공유 요청 반환을 전송 완료로 집계하지 않는다. 자유 입력·근무 날짜·근무 순서·메모·자체 식별자는 이벤트에 넣지 않는다.
- **SDK 준비:** `@apps-in-toss/web-framework` 3.7.0 → **3.9.0**, `@apps-in-toss/devtools` 설치본 3.8.0 → **3.9.0**을 목표로 의존성 변경·API 호환·자동 검사·실기기·출시 번들 점검·되돌리기 절차를 정한다. 실제 업데이트는 구현 단계에서 한다.
- 이번 요청은 **명세 작성과 업데이트 준비**다. 기존 소스·패키지·정식 명세·콘솔 설정·배포본을 변경하지 않는다. 새 기능인 데이터 백업/복원이나 별도의 인수인계 문서 정비는 포함하지 않는다.

## Capabilities

### New Capabilities

- `usage-analytics`: 핵심 사용 행동의 이벤트 계약, 전송 시점, 데이터 최소화, 실패 격리, 콘솔 지표 연결 및 검증 범위.

### Modified Capabilities

- `schedule-export`: “캘린더 알림 안내 줄”과 “캘린더 파일 보내기” — 현재 설정·기본 알림 안내, 캘린더 앱별 재가져오기 차이, SDK 결과가 실제 전송 완료를 뜻하지 않는다는 기존 경계 유지.
- `calendar-reminder`: “캘린더 알림 안내” — 이미 가져온 일정에 대한 자동 반영·갱신을 보장하지 않는 안내.

## Impact

- 구현 대상: `src/components/ExportSheet.tsx`, `CalendarReminderScreen.tsx`, `CalendarScreen.tsx`, `src/App.tsx`, 작은 분석 전송 모듈 `src/platform/analytics.ts`, 관련 단위·브라우저 E2E 검사, `package.json`·`package-lock.json`.
- SDK: 공식 npm에 두 패키지의 3.9.0 배포를 확인했다. Devtools 3.9.0은 Node >=24와 SDK 3.x 호환 범위를 요구하며 현재 Node 24.21.0은 이를 충족한다. 새 SDK의 타입·실제 실행 호환은 아직 검증하지 않았다.
- 데이터: 근무표·메모의 로컬 저장 구조(v3/v1)는 유지한다. 새 행동 이벤트는 SDK 분석 경로로 전송되며 SDK가 자동으로 붙이는 식별 파라미터까지 “없는 데이터”라고 설명하지 않는다.
- 운영: 핵심 지표의 기존 설정은 MCP 서버 미지원으로 미확인이다. 콘솔 웹에서 기존 값을 보존하며 변경안을 확인한 뒤 연결한다. QR/mock 검사는 이벤트가 운영 콘솔에 집계되었다는 증거가 아니며 운영 집계는 출시 후 별도 확인한다.
- 기준일: 2026-10-26. 라이브 v1.3 `20261021-27`, 검수 승인·앱 정보 승인·미리보기 8장 등록을 콘솔에서 확인했다. 로컬 `main`과 원격 최신 `965bdbe`의 차이는 README·인수인계 문서뿐이며 이 명세에서 임의 동기화하지 않는다.

### SDK mock 실패 주입 보정

`day-entries.mjs` 첫 실행은 58/59였다. 전체 초기화 실패 검사에서 `localStorage.removeItem` 예외를 주입했지만 Devtools 3.9.0의 `remove`는 그 예외를 경고 후 처리해 SDK 호출을 성공으로 반환한다. 최소 재현에서도 설정 키가 남은 채 앱이 초기화 성공 화면으로 이동했다.

같은 실패를 앱이 받는 `Storage.removeItem` Promise 거부로 주입하면 초기화 화면·오류 안내·기존 저장값이 유지됨을 확인했다. E2E의 실패 주입 위치를 SDK 경계로 옮겼으며 앱의 초기화 구현은 변경하지 않았다. 해당 E2E는 59/59 재검사 통과했다.

## 실기기 확인 준비

사용자 답변: Galaxy S26 Ultra에서 삼성·구글 캘린더 확인 가능. 테스트 번들 `20261026-28`과 C01~C06 안내 뒤 **“정상 작동 확인”** 응답을 받았다. 두 캘린더에 대한 일괄 정상 확인으로 기록하며, 앱별 일정 수·중복 처리·알림 시각 등 사례별 상세 결과를 추정해 채우지 않는다.

**캘린더 구분 정정(사용자 확인):** Galaxy S26 Ultra의 내장 캘린더 앱은 `내 폰 저장`, `구글 캘린더`, `삼성 캘린더`, `리마인더` 네 캘린더를 하나의 “캘린더” 앱으로 묶어 관리한다. 사용자 확인으로 ICS 파일은 `내 폰 저장`에 들어가는 방식으로 동작한다. 따라서 “삼성 캘린더”와 “구글 캘린더” 열은 별도 앱의 결과가 아니며, 열을 나누려면 가져온 대상 캘린더 이름(네 가지 중 하나)을 사례마다 기록한다. 로컬 `내 폰 저장`은 계정 동기화를 거치지 않으므로, 구글·삼성 계정 동기화 결과를 ICS 가져오기 결과로 해석하지 않는다.

**사용자 상세 보고(C02·C03, 캘린더 앱 미지정):** 같은 파일 재가져오기와 근무 변경 뒤 재가져오기에서 **일정이 갱신되지 않았다.** 변경 뒤 캘린더 앱에 덮어쓰기 또는 저장 버튼이 나타나지 않았다. 앞의 “일괄 정상 응답”은 이 상세 결과와 맞지 않으므로 C02·C03은 **차이 있음**으로 정정한다. 아직 기록되지 않은 항목은 다음과 같다: 캘린더 앱 이름·버전, 가져오기 후 일정 수, 중복 여부, 변경 전후 값, 같은 UID 유지 여부. 이 정보를 확인한 뒤 판정을 확정한다.

# Tasks

이 문서는 이번 변경의 유일한 구현 체크리스트다. 실제 구현·검증이 끝난 항목만 완료로 표시한다. `design.md`의 명령·표는 이 작업들의 근거이며 별도의 완료 목록이 아니다.

## 1. SDK 3.9.0 업데이트와 기존 동작 기준선

- [x] 1.1 `package.json`·`package-lock.json`에서 SDK·Devtools를 각각 정확한 3.9.0으로 업데이트한다. React·TDS·Vite·TypeScript는 유지한다. 확인: `npm ls @apps-in-toss/web-framework @apps-in-toss/devtools @apps-in-toss/cli`에서 버전·peer 오류가 없고 lockfile의 다른 변경에 설명이 있다. 참조: design “SDK 업데이트 준비”.
- [x] 1.2 기능 코드를 바꾸기 전에 `npm ci`, `npm run typecheck`, `npm run test:tz`로 SDK만 바뀐 상태를 검사한다. 확인: 재설치와 서울·뉴욕·UTC 검사가 모두 성공하고 실제 테스트 개수를 기록한다. 과거 367개 결과를 이번 성공으로 복사하지 않는다.
- [x] 1.3 SDK 3.9.0에서 기존 E2E 14종과 `npm run build:adtest`를 확인한다. 저장·복원·초기화, 식별키, 안전 영역, 내비게이션·뒤로가기, 배너, PNG/ICS·연속 내보내기를 포함한다. 확인: `scripts/e2e/README.md`의 실제 스크립트 목록과 실행 결과가 대응하고 SDK 교체로 생긴 실패만 최소 수정한다. 새 SDK에 없는 API를 추측해 쓰지 않는다.

## 2. 알림 안내 문구 정리

- [x] 2.1 `ExportSheet.tsx`의 켜짐·꺼짐 문구와 공통 기본 알림 주의 문구를 변경한다. `calendar-reminder.mjs`·`month-export.mjs`의 관련 기대값을 갱신한다. 확인: 기본 21시·변경 20시·꺼짐 상태에서 `schedule-export` “캘린더 알림 안내 줄”의 두 시나리오가 통과한다.
- [x] 2.2 `CalendarReminderScreen.tsx`에서 이미 가져온 일정의 자동 갱신을 보장하지 않는 안내로 수정한다. 확인: `calendar-reminder` “캘린더 알림 안내” 시나리오가 E2E에서 통과하고, 토글·시각·저장·실패 시 되돌림은 그대로 동작한다.
- [x] 2.3 기존 시각 감사와 관련 내보내기·알림 E2E로 360px·390px 화면을 확인한다. 확인: 새 안내가 잘리지 않고 가로 스크롤·11px 미만 글자·44px 미만 기존 조작 영역 회귀가 없다. VALARM·UID·파일 이름·저장 형식의 의도하지 않은 diff가 없다.

## 3. 핵심 사용 행동 기록

- [x] 3.1 `src/platform/analytics.ts`에 고정된 세 이벤트의 전송 함수와 단위 검사를 추가한다. 확인: `usage-analytics` “이벤트 속성 최소화”·“분석 실패 격리”에 따라 정확한 이름·허용 속성만 전송하고 동기 예외·Promise 거부·응답 지연·미지원 상황에서 호출자 흐름이 막히지 않는다. 자체 큐·저장·재시도가 없다.
- [x] 3.2 `App.tsx`의 패턴 저장 성공 뒤 이벤트를 연결한다. 저장소 성공·실패와 이력 불러오기만 한 경우를 분리해 회귀 검사를 추가한다. 확인: “근무 패턴 저장 이벤트”·“렌더링과 기록 횟수의 분리” 시나리오가 통과하고 기존 저장 실패 안내·화면 이동이 유지된다.
- [x] 3.3 `CalendarScreen.tsx`의 내보내기 처리 시작과 결과 반환에 이벤트를 연결한다. 확인: 이미지/캘린더의 요청·`opened|failed|unsupported` 값이 계약과 같고, 시트 열기/닫기·비활성 재누르기는 요청을 만들지 않는다. 공유 취소는 SDK 반환 이상으로 구분하거나 완료로 표시하지 않는다.
- [x] 3.4 새 `scripts/e2e/usage-analytics.mjs`로 `window.__ait.state.analyticsLog`를 확인한다. 확인: 세 이벤트 계약, 저장 실패 무기록, 렌더 중복 없음, 독립 재시도는 각각 기록, 실패·미지원 결과, 분석 오류에도 업무 성공, 이름·날짜·패턴·메모·식별키 누출 없음이 통과한다. SDK가 추가하는 공통 속성과 앱 페이로드를 구분한다.
- [x] 3.5 분석 E2E 실행 방법과 데이터 경계를 관련 문서에 기록한다. 확인: `scripts/e2e/README.md`에 실제 스크립트와 검사 범위를 연결하고 README에서 근무표·메모의 로컬 저장과 SDK 행동 분석을 혼동하지 않게 한다. 앱 설명은 이미 관련 내용이 맞으면 수정하지 않으며 새 콘텐츠·광고 기능을 추가하지 않는다.

## 4. 삼성·구글·iOS 캘린더 실기기 확인

- [x] 4.1 `build:adtest` 번들과 실제 기기별 테스트 캘린더·가상 데이터를 준비한다. 확인: 번들 ID, 기기·OS·토스·캘린더 앱 버전, 시간대·기본 알림·권한을 기록하고 개인 기존 일정과 분리한다. 토스·캘린더 앱 버전은 번호 없이 사용자 확인 "최신"으로 기록할 수 있다(2026-10-27 사용자 결정). 업로드·테스트 푸시는 해당 실행 요청 범위에서만 하며 검수 신청·출시는 하지 않는다.
- [ ] 4.2 삼성 캘린더에서 design C01~C06을 수행한다. 확인: 최초/동일 파일/변경 파일 가져오기, 켜기·끄기·시각 변경·휴무 제외, 반복 보내기·취소, 실제 알림 도착의 결과와 증거를 사례별로 기록한다. 기본 앱의 실제 이름·버전을 확인한다.
- [ ] 4.3 구글 캘린더에서 C01~C06을 수행한다. 확인: 삼성 결과를 복사하지 않고 일정 수·중복·변경 반영·기본 알림·실제 도착을 별도로 기록한다. 가져오기 경로가 지원되지 않으면 사용한 공식 경로와 제한을 명시한다.
- [ ] 4.4 iOS 캘린더에서 C01~C06을 수행한다. 확인: iOS 공유/파일 가져오기, 일정·알림·반복 보내기 결과를 별도 기록한다. 기기가 없거나 실행하지 못한 사례는 미실행으로 두고 iOS 검증 완료로 표시하지 않는다.
- [ ] 4.5 세 환경의 결과를 비교하고 실제 문제를 분류한다. 확인: 파일 자체 오류는 최소 수정 후 관련 자동 검사와 같은 기기 사례를 다시 통과시키고, 외부 앱 차이는 안내와 결과 기록에 반영한다. 미실행 환경·실제 도착 미확인·남은 문제를 구분해 남긴다. 외부 일정 자동 삭제·동기화 기능을 추가하지 않는다.

## 5. 콘솔 핵심 지표 연결안 준비

- [x] 5.1 콘솔 웹에서 기존 활성 지표·전환 지표·대표 여부·조건을 확인해 현재 값과 design의 연결안을 비교한다. 확인: 기존 설정 근거와 유지/변경 대상을 구분한다. MCP가 계속 미지원이면 반복 호출하지 않으며, 웹에서도 확인하지 못하면 미확인 상태와 필요한 사용자 확인을 기록한다.
- [x] 5.2 대표 후보 “근무 패턴 저장”과 보조 후보 “근무표 공유 요청 반환”의 이벤트·조건·의미를 정리한다. 확인: `usage-analytics` “핵심 지표의 의미”와 일치하고 `opened`를 실제 전송 완료로 부르지 않는다. 사용자 확인 전 기존 지표를 바꾸지 않고, 운영 집계 미확인을 코드 검증 완료와 분리한다.

## 6. 통합 검증·출시 준비

- [x] 6.1 타입 검사·3개 시간대 단위 검사·기존 E2E 14종·새 분석 E2E를 통합 실행한다. 확인: 실제 결과와 개수를 기록하고 요청 1~3·SDK 변경에 대응하는 검사가 모두 통과한다. 새 실패나 변경 없이 이미 통과한 검사를 불필요하게 반복하지 않는다.
- [x] 6.2 출시용 빌드를 준비하고 저장 호환·의존성·번들 내용을 확인한다. 확인: 선언과 lockfile의 SDK/Devtools 3.9.0, 기존 v3/v1 데이터 복원, 실제 광고 설정 유지, Devtools/mock 실행 코드·테스트 광고 ID·진단 코드 제외를 확인한다. 실제 광고 ID를 출력·문서화하지 않는다.
- [x] 6.3 실제 자동·실기기 결과, 콘솔 연결 준비 상태, 미실행 환경을 명세 및 관련 인수인계 기록과 대조한다. 확인: 구현 작업의 완료와 미확인을 구분하고 `openspec validate improve-release-quality-and-analytics --strict`·`git diff --check`가 통과한다. 검수 신청·라이브 변경·아카이브는 별도 요청 전에 실행하지 않는다.

## Workflow follow-up

- 자동 검사·실기기 결과와 남은 확인을 사용자가 검토한 뒤, 별도 요청에 따라 OpenSpec 동기화·아카이브와 해당 변경만의 커밋·병합·푸시를 진행한다. 기존 기능 브랜치를 임의 삭제하지 않는다.
- 출시·검수 요청은 사용자가 요청할 때만 진행한다. 기존 라이브 v1.3 `20261021-27`을 승인 없이 변경하지 않는다.
- 새 버전 출시 뒤 실제 행동을 수행하고 다음 날 이후 이벤트 수집을 확인한다. 콘솔에서 현재 지표와 변경안을 사용자가 확인한 후 연결하고 다음 날 이후 적용을 확인한다. 이벤트 목록에 새 이벤트가 아직 없으면 등록 완료로 표시하지 않는다.
- 마지막 운영 집계 확인은 아카이브 시점과 독립된 후속 확인이다. 기기 테스트나 개발 mock 통과만으로 운영 수집 완료를 선언하지 않는다.

# Spec Delta

## Purpose

근무 패턴 저장과 근무표 내보내기의 실제 이용을 최소한의 행동 이벤트로 측정한다. 근무 데이터는 전송하지 않고, 분석 실패가 앱 기능을 막지 않으며, 개발 환경 확인과 운영 콘솔 집계를 구분한다.

## ADDED Requirements

### Requirement: 근무 패턴 저장 이벤트
앱은 사용자가 근무 패턴을 저장해 로컬 저장이 성공한 뒤 `turncal_pattern_saved` 이벤트를 SHALL 한 번 기록한다. 최초 등록·기존 패턴 수정·이력 불러오기 후 저장에 같은 이벤트를 사용한다. 입력 오류, 저장 실패, 불러오기만 한 상태, 재실행에 의한 복원에는 기록해서는 MUST NOT 된다. 앱이 추가하는 속성은 없다.

#### Scenario: 저장 성공
- **WHEN** 유효한 근무 패턴을 저장해 로컬 저장이 성공한다
- **THEN** `turncal_pattern_saved`가 한 번 기록되고 기존과 같이 달력으로 돌아간다

#### Scenario: 저장 실패와 단순 복원
- **WHEN** 저장이 실패하거나 앱을 다시 열어 저장된 패턴을 읽는다
- **THEN** `turncal_pattern_saved`가 기록되지 않는다

#### Scenario: 이력 불러오기와 저장
- **WHEN** 이력을 편집기로 불러온다
- **THEN** 이벤트가 없고, 사용자가 이후 저장을 성공한 경우에만 한 번 기록된다

### Requirement: 내보내기 요청 이벤트
앱은 내보내기 시트에서 실제 처리 가능한 이미지·캘린더 파일 선택을 받아 처리를 시작할 때 `turncal_export_requested`를 SHALL 한 번 기록한다. 속성 `format`은 `image` 또는 `calendar`이다. 시트를 여는 것, 닫는 것, 처리 중 비활성 선택지 누르기에는 기록해서는 MUST NOT 된다.

#### Scenario: 선택 뒤 처리 시작
- **WHEN** 사용자가 활성 상태의 캘린더 파일 보내기를 선택한다
- **THEN** `format=calendar`인 요청 이벤트가 한 번 기록된다

#### Scenario: 요청하지 않은 행동
- **WHEN** 사용자가 시트를 닫거나 처리 중인 선택지를 다시 누른다
- **THEN** 새 요청 이벤트가 기록되지 않는다

### Requirement: 내보내기 결과 이벤트
앱은 시작한 내보내기 처리의 결과를 `turncal_export_result`로 SHALL 한 번 기록한다. 속성은 `format=image|calendar`, `result=opened|failed|unsupported`만 사용한다. `opened`는 공유 SDK 요청이 오류 없이 반환되었다는 뜻이며 파일 전송·저장·캘린더 가져오기 완료를 의미해서는 MUST NOT 된다. 결과를 알 수 없는 공유 취소 이벤트를 만들어서는 MUST NOT 된다.

#### Scenario: 공유 요청 반환 또는 취소
- **WHEN** 공유 SDK가 오류 없이 반환되거나 사용자가 공유 창에서 취소해도 같은 결과가 반환된다
- **THEN** `result=opened`만 기록하며 “전송 완료”, “저장 완료”, “공유 취소 확인”으로 집계하지 않는다

#### Scenario: 실패 또는 미지원
- **WHEN** 내보내기 결과가 오류 또는 미지원으로 끝난다
- **THEN** 각각 `result=failed` 또는 `result=unsupported`가 한 번 기록되고 기존 안내가 유지된다

### Requirement: 이벤트 속성 최소화
앱이 추가하는 이벤트 속성은 위에서 정한 `format`·`result` 값으로 SHALL 제한한다. 이름, 메모, 근무 날짜·순서·유형·시간, 파일 이름·공유 링크, 자유 입력, 원시 오류 메시지, 앱이 보관한 식별키를 추가해서는 MUST NOT 된다. SDK가 자동 포함하는 기본 식별 파라미터와 앱이 추가하는 속성은 구분해 설명해야 한다(MUST).

#### Scenario: 사용자 데이터 제외
- **WHEN** 이름·메모·사용자 정의 근무 유형이 있는 상태에서 패턴 저장 또는 내보내기를 한다
- **THEN** 앱이 만든 분석 페이로드에는 고정 이벤트 이름과 허용된 열거 값만 있고 사용자 입력 내용은 없다

### Requirement: 분석 실패 격리
분석 전송의 동기 예외, 비동기 거부, 미지원, 응답 지연은 저장·내보내기·화면 전환을 막아서는 MUST NOT 된다. 앱은 분석 전송 완료를 기다리거나 실패 안내를 사용자에게 표시해서는 MUST NOT 되며, 분석 전용 로컬 저장·재전송 큐·주기적 재시도·추가 자체 서버를 만들지 않는다(MUST NOT).

#### Scenario: 분석 서버 오류
- **WHEN** 분석 호출이 예외를 던지거나 거부되거나 끝나지 않는다
- **THEN** 패턴 저장·공유 요청은 원래 결과대로 진행되고 미처리 오류·분석 오류 팝업·자동 재시도가 생기지 않는다

### Requirement: 렌더링과 기록 횟수의 분리
이벤트는 사용자 행동을 처리하는 흐름에서 SHALL 기록한다. 화면 재렌더링, 상태 반영, 개발 모드의 중복 효과 실행만으로 추가 기록해서는 MUST NOT 된다. 사용자가 별도로 성공시킨 두 저장 또는 두 내보내기는 각각 독립된 행동으로 기록한다.

#### Scenario: 재렌더링과 독립된 재시도
- **WHEN** 저장 뒤 화면이 다시 그려지고 사용자가 나중에 별도로 다시 저장한다
- **THEN** 재렌더링은 이벤트를 추가하지 않고 두 번의 성공한 저장에 총 두 이벤트만 기록된다

### Requirement: 핵심 지표의 의미
대표 전환 후보는 `turncal_pattern_saved`가 발생한 사용자, 보조 전환 후보는 `turncal_export_result`의 `result=opened`가 발생한 사용자로 SHALL 정의한다. 보조 전환의 이름·설명은 공유 요청 반환임을 드러내야 한다(MUST). 기존 활성·전환 지표는 확인 없이 교체해서는 MUST NOT 되며, 이벤트 호출 횟수를 고유 사용자 수나 실제 전송 완료 수로 간주해서는 MUST NOT 된다.

#### Scenario: 콘솔 설정 확인
- **WHEN** 운영 콘솔에서 핵심 지표를 연결한다
- **THEN** 기존 설정과 비교한 변경안을 남기고 사용자가 확인한 설정만 반영하며, 기존 상태를 조회하지 못한 경우 미확인으로 기록한다

### Requirement: 검증 환경의 구분
개발 mock·QR 검사는 이벤트 이름·속성·호출 횟수를 검증하는 근거로만 SHALL 사용한다. 운영 콘솔 수집 완료는 출시된 버전의 실제 행동과 집계 화면에서 별도로 확인해야 한다(MUST). 집계 지연·빈 응답·조회 불가를 수집 성공이나 이용자 0명으로 단정해서는 MUST NOT 된다.

#### Scenario: 개발 검사와 운영 집계
- **WHEN** 브라우저 mock의 이벤트 목록에 세 이벤트가 기대한 값으로 나타난다
- **THEN** 로컬 검사는 통과로 기록하되 운영 집계는 별도 미확인으로 남겨 출시 후 확인한다

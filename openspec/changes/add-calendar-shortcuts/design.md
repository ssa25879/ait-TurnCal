# Design

## Context

동기는 proposal.md 참고. 현재 구조에서 영향이 있는 사실(2026-10-15 `main` 기준):

- `App.tsx`의 `View`는 `{ kind: "pattern"; fromCalendar?: boolean }`로 근무 패턴 설정 화면의 출처를 이미 구분한다. 달력의 [근무 패턴 등록하기]가 이 값을 켜고, 뒤로가기(`toSettingsMenu` 핸들러)와 폐기 확인 목적지(`DiscardTarget`)가 `fromCalendar`이면 달력으로 간다.
- `decideBackAction`(`useBackHandler.ts`)은 화면 종류와 저장 여부·변경 여부만 보고 동작을 정하며 목적지는 호출자(App)의 핸들러가 정한다. 따라서 출처 분기는 App 쪽에서만 하면 되고 결정 함수는 바뀌지 않는다.
- `names` 뷰(`NamesScreen`)는 출처 구분이 없고 `saveNames`가 저장 뒤 `toSettingsMenu()`로 간다. 이름 화면의 뒤로가기는 `confirmDiscard`/`to-settings-menu`로 설정 목록에 간다.
- 근무 패턴 저장(`savePattern`)과 패턴 초기화(`runResetPattern`)는 이미 달력으로 이동하므로 출처와 무관하게 달력 복귀는 만족한다.
- `CalendarScreen`은 이름 헤더(`schedule-header`) 아래에 오늘·내일 카드, 월 이동, 달력, [설정] 버튼, 배너 순으로 있다. 패턴이 없으면 안내 카드가 오늘·내일 카드 위에 있다.

## Goals / Non-Goals

**Goals:**
- 달력에서 한 번의 탭으로 근무 패턴 수정·이름 수정 화면을 연다.
- 바로가기로 연 화면의 뒤로가기·폐기 확인·저장 후 이동이 모두 달력으로 일관되게 돌아온다.
- 기존 설정 목록 경로의 동작과 뒤로가기 계층을 바꾸지 않는다.

**Non-Goals:**
- 화면 설정·초기화 바로가기(요청 범위 밖).
- 이력 퀵스왑, 설정 목록 개편.
- 새 오버레이·바텀시트·외부 이동(출시 가이드 위험 없음 유지).

## Decisions

### 1. 이름 뷰에도 같은 출처 표시(`fromCalendar`)를 쓴다
`View`의 `names`를 `{ kind: "names"; fromCalendar?: boolean }`로 넓히고, 패턴 뷰와 같은 방식으로 세 곳을 분기한다: ① 뒤로가기 핸들러 `toSettingsMenu` ② 폐기 확인 목적지 `DiscardTarget` ③ 저장 후 이동(`saveNames`). 출처 표시는 뷰 값에 들어 있어서 화면이 바뀔 때 자동으로 사라지고 별도 상태·참조가 필요 없다.
- 이유: 이미 검증된(E2E 39개) 방식을 재사용하면 새 상태 기계가 생기지 않는다. `decideBackAction`과 그 단위 테스트는 건드리지 않는다.
- 대안: ① 뒤로가기 스택(히스토리 배열) 도입 — 화면이 열 개 남짓인 앱에 과하고 기존 계층 규칙과 이중이 되어 거부. ② 바로가기에서 설정 목록을 거쳐 이동 — 요구(목록 생략)와 반대라 거부.

### 2. 이동 헬퍼를 한 곳으로 모은다
`go({ kind: "pattern", fromCalendar: true })`처럼 바로가기 진입을 `openFromCalendar(kind)` 같은 작은 함수로 모아, 달력의 세 콜백(등록하기·패턴 수정·이름 수정)이 같은 경로를 쓰게 한다. 폐기 확인 목적지 계산도 "현재 뷰가 달력 출처인가"를 한 함수로 묻는다.
- 이유: 출처 분기가 두 뷰에 걸쳐 중복되지 않게 하고 이후 화면 설정 등으로 확장하기 쉽게 한다.

### 3. 버튼은 달력 아래·[설정] 버튼 위 한 줄, 폭 균등 분할
`CalendarScreen`의 달력 격자 아래(`bottom-action` 안, [설정] 버튼 바로 위)에 TDS `Button`(`variant="weak"`, `medium`) 두 개를 한 줄에 같은 폭으로 놓는다(`display="full"`로 한 줄을 반씩 나눔). 패턴이 없으면 [이름 수정] 하나만 한 줄 전체 폭으로 보인다. 실기기 피드백으로 위치를 이름 헤더 아래에서 달력 아래로, 크기를 `large`에서 `medium`으로 바꿨다(헤더 아래에 두면 오늘·내일 카드가 밀리고 버튼이 커 보임). [설정] 버튼 위에 두므로 배너와의 간격 규칙(설정 버튼 아래 32px)은 그대로다.
- 이유: 가로 스크롤·겹침이 구조적으로 불가능하고, 터치 영역이 충분하다(TDS 버튼 높이 확보). 글자 11px 이상 규칙을 만족한다.
- 대안: ① 헤더 오른쪽 아이콘 버튼 — 긴 이름과 겹치고 의미가 모호해 거부. ② 달력 하단 [설정] 옆에 배치 — 스크롤해야 보이고 배너와의 간격 규칙(32px)에 영향을 줘 거부. ③ 이름 글자 자체를 눌러 수정 — 발견하기 어려워 거부.

### 4. 패턴이 없으면 [근무 패턴 수정]을 숨긴다
`timeline.current === null`이면 안내 카드의 [근무 패턴 등록하기]가 같은 화면(근무 패턴 설정, 첫 등록)을 열므로 버튼을 중복 노출하지 않는다.

### 5. 저장된 설정이 없으면 메모리 기본 설정으로 빈 달력(등록 안내 화면 제거)
저장소가 비어 있으면(첫 실행·전체 초기화 뒤·재실행) `settings` 상태를 `createDefaultSettings()`(패턴 없음)로 두고 달력을 연다. 저장하지는 않는다. 그러면 "설정 있음"이 되어 모든 뒤로가기 규칙(달력은 종료, 등록하기로 연 화면은 달력 복귀)이 한 가지로 통일된다. 등록 안내 화면(`setup-intro` 뷰·`SetupIntro` 컴포넌트·`decideBackAction`의 해당 화면)은 없앤다. 설정 읽기 오류(`load-error`)는 그대로이고 그 화면의 [다시 설정하기]는 기본 설정이 없으므로 종료 규칙을 유지하며 `LoadError`가 쓰던 `.intro*` 스타일은 공용 클래스로 바꾼다.
- 이유: 사용자 결정("첫 실행도 빈 달력")이며 저장 형식·`empty` 판정은 그대로다. 전체 초기화 뒤 재실행도 같은 화면이라 "저장소가 비었을 때"를 구분할 필요가 없다. 기본 설정을 저장하지 않으니 이후 이름·패턴을 저장할 때 처음 설정이 생긴다.
- 대안: ① 전체 초기화 표식만 저장해 첫 실행 안내를 유지 — 구분용 저장 상태가 생겨 거부(사용자가 첫 실행도 빈 달력을 선택). ② 전체 초기화 뒤에만 빈 달력 — 재실행 때 구분이 안 돼 거부.

## Risks / Trade-offs

- [헤더 아래 버튼 줄이 달력 첫 화면을 밀어 오늘·내일 카드나 배너가 가려질 수 있음] → 두 해상도 스크린샷과 E2E(`today-summary`의 배너 간격 32px 검사 포함 전 종)로 확인하고, 높이가 문제면 버튼 줄을 작은 크기로 줄인다.
- [출처 분기 누락으로 일부 경로에서 설정 목록으로 튐] → 분기점 세 곳(뒤로가기·폐기·저장)을 tasks에 나열하고 E2E로 경로별(변경 없음·폐기·폐기 취소·저장·패턴 초기화) 확인한다.
- [기존 E2E가 달력의 버튼 개수·텍스트에 의존] → 전 종 실행으로 회귀 확인. 새 버튼 텍스트("근무 패턴 수정", "이름 수정")가 기존 선택자(`getByText("근무 패턴")` 등 부분 일치)와 겹치지 않는지 점검한다.

- [메모리 기본 설정 상태에서 이름·화면 설정을 저장하면 그때 처음 설정이 저장됨] → 의도한 동작이며 E2E(빈 달력에서 등록 → 저장)로 확인한다.

## Migration Plan

- 저장 데이터 변경·마이그레이션 없음.
- 배포: 기능 브랜치 → 단위·시간대·E2E 통과 → `build:adtest`로 실기기 확인 → 다른 업데이트와 함께 실제 광고 ID 번들로 한 번에 출시(사용자 계획).
- 롤백: 콘솔에서 이전 번들로 되돌린다.

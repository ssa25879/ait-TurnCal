# Proposal

## Why

근무제가 바뀌어 패턴을 수정하면 지금은 **이미 지난 날짜의 근무도 새 패턴으로 다시 계산**된다. 지난 근무 기록(달력의 과거 칸)이 실제와 달라지는 것이 기획서 8장의 "알려진 한계"이고, 출시 후 첫 개선 후보로 꼽은 항목이다. 한편 입력을 잘못해서 고치는 경우에는 지난 날짜까지 바뀌는 것이 맞으므로, 두 경우를 모두 지원해야 한다.

## What Changes

- 근무 패턴을 저장할 때 **적용 범위**를 고른다: **오늘부터 적용**(기본값, 지난 날짜는 이전 패턴 유지) 또는 **전체 기간에 적용**(지금 동작, 잘못 입력한 것 수정).
- "오늘부터 적용"으로 바꾼 패턴은 **이력**으로 쌓이고, 달력·날짜 화면·오늘/내일 요약은 각 날짜에 **그날 적용되던 패턴**으로 근무를 계산한다.
- 근무 패턴 설정 화면에 읽기 전용 **패턴 이력** 목록(적용 기간과 근무 순서)을 보여 준다. 개별 이력의 수정·삭제는 이번 범위 밖이다.
- 패턴을 바꾸지 않고 저장하면 이력이 늘지 않는다. 첫 등록(저장된 패턴이 없음)에는 적용 범위 선택이 없다.
- 근무 패턴 초기화는 이력도 함께 지운다.
- 저장 형식은 `version: 3`을 유지하고 **선택 필드** `patternHistory`를 추가한다. 기존 저장 데이터는 이력이 없는 상태로 그대로 읽히고(마이그레이션 불필요), 이전 번들로 되돌려도 이전 앱이 새 필드를 무시해 계속 동작한다.

## Capabilities

### New Capabilities
- `pattern-history`: 날짜별 적용 패턴 결정, 저장 시 적용 범위(오늘부터/전체)와 이력 갱신 규칙, 이력 상한, 읽기 전용 패턴 이력 목록

### Modified Capabilities
- `shift-pattern-settings`: "편집 내용 확정" — 저장 성공 결과가 적용 범위에 따라 달라지고, 변경이 있을 때 적용 범위 선택을 제공한다
- `settings-persistence`: "설정 저장 형식"·"저장 데이터 검증" — 선택 필드 `patternHistory`의 저장 형식과 검증
- `settings-reset`: "근무 패턴 초기화" — 이력도 함께 지운다

## Impact

- 코드: `src/domain/`(이력 계산 새 모듈, `types.ts`), `src/storage/scheduleStorage.ts`(필드·검증), `src/storage/reset.ts`, `src/App.tsx`(저장 흐름·이력 전달), `src/components/SettingsScreen.tsx`(적용 범위·이력 목록), `Calendar.tsx`·`CalendarScreen.tsx`·`DayScreen.tsx`·`TodaySummary.tsx`·`src/domain/summary.ts`(패턴 대신 이력 포함 패턴 정보 전달), `src/style.css`.
- 테스트: 도메인·저장소·초기화 단위 테스트 추가, 브라우저 E2E 추가, 저장 흐름을 가정한 기존 E2E 재확인.
- 호환성: 저장 키·`version` 불변. 이력이 없는 데이터는 이전과 같은 동작. 출시 후 번들 롤백 시 이전 앱은 현재 패턴으로 모든 날짜를 계산(이전 동작)한다.
- 의존성·권한·네트워크 변경 없음. 출시 가이드: 새 바텀시트·외부 이동·권한 없음(적용 범위는 설정 화면 안에서 선택).

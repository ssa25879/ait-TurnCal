# Design

## Context

동기는 proposal.md 참고. 현재 구조에서 설계에 영향을 주는 사실:

- 근무 패턴은 `WorkPattern { startDate, cycle }` 하나이며 `StoredSettingsV3.pattern`에 저장된다(초기화 후 `null`). 근무 계산 `getShift(date, pattern)`은 순수 함수이고, `getEffectiveShift(date, pattern, day)`가 날짜 세부 내용 분류를 얹는다.
- 패턴을 쓰는 곳은 `Calendar`(칸마다), `DayScreen`, `TodaySummary`/`domain/summary.ts`, 설정 편집(`settingsDraft`), `reset.ts`뿐이다. 모두 props로 `pattern`을 받는다.
- 저장은 `version: 3` 단일 키이며 이전 버전(v1·v2) 읽기 시 변환만 하고 다시 쓰지 않는다. 앱이 모르는 상위 버전은 손상 데이터처럼 다루되 저장값을 지우지 않는다.
- 설정 편집은 `PatternDraft`(근무 순서 + 오늘 위치)이고 저장 시 `draftToPattern`이 `startDate = today - todayIndex`를 만든다. 오늘 위치 기반이라 `startDate`는 같은 일정에 대해 주기의 배수만큼 다른 값이 될 수 있다.
- 뒤로가기·오버레이 규칙(`miniapp-shell`)은 바텀시트·다이얼로그를 오버레이로 다룬다. 새 UI에 오버레이를 추가하면 이 규칙과 상호작용한다.

## Goals / Non-Goals

**Goals:**
- 패턴을 바꿔도 지난 날짜의 근무가 유지되게 한다(기본 동작).
- 잘못 입력한 패턴을 고치는 경우를 위해 지금 동작(전체 기간 적용)도 남긴다.
- 기존 저장 데이터를 마이그레이션 없이 그대로 읽고, 번들을 롤백해도 이전 앱이 깨지지 않게 한다.
- 달력·날짜 화면·요약이 항상 같은 근무를 보여 준다(판정 지점을 하나로 모은다).

**Non-Goals:**
- 이력 항목의 개별 수정·삭제, 임의 날짜부터 적용(적용 시작일은 항상 저장한 날 = 오늘).
- 날짜 세부 내용(`turncal.entries`)이나 이름·테마 같은 다른 설정의 이력.
- 서버·동기화·백업.
- 근무 유형 사용자 정의(별도 후보).

## Decisions

### 1. 저장은 `version: 3`에 선택 필드 `patternHistory`를 더한다 (v4로 올리지 않음)
현재 패턴은 지금처럼 `pattern`에 두고, **교체된 이전 패턴**만 `patternHistory: [{ until, pattern }]`에 날짜순으로 쌓는다. `until`은 "이 날짜 전날까지 적용"이다. 날짜 d의 패턴은 `d < until`을 만족하는 첫 항목의 패턴이고, 없으면 현재 패턴이다.
- 이유: ① 기존 v3 데이터에는 필드가 없을 뿐이라 **마이그레이션이 없다**. ② 이전 번들(`20261013-8` 등)은 모르는 필드를 무시하고 `pattern`으로 모든 날짜를 계산하므로 **롤백이 안전**하다(v4로 올리면 이전 앱이 "더 새로운 버전" 오류로 설정을 읽지 못한다). ③ `settings.pattern`을 쓰는 코드(설정 편집·초기화)를 그대로 둘 수 있다.
- 대안: ① 전 패턴을 `patterns: [{from, ...}]`로 바꾸는 v4 — 롤백 불가, 읽기·쓰기 경로 전부 수정. ② 별도 저장 키 — 설정과 이력의 원자성이 깨져 불일치 위험.

### 2. 판정 지점은 도메인 모듈 하나(`src/domain/patternHistory.ts`)
- `PatternTimeline { current: WorkPattern; history: PastPattern[] }`
- `resolvePattern(date, timeline): WorkPattern` — 위 규칙으로 그날 패턴을 고른다.
- `applyPatternChange(timeline | null, next, scope, today): PatternTimeline` — 저장 시 이력 갱신 규칙(아래 3).
- `isSameSchedule(a, b)` — 같은 근무 순서이고 위상(기준일 차이를 주기로 나눈 나머지)이 같으면 같은 일정.
- `describeTimeline(timeline)` — 목록용 행(적용 기간, 근무 순서)을 최신순으로 만든다.
컴포넌트는 `getEffectiveShift(date, resolvePattern(date, timeline), day)`로 호출한다. `getShift`·`getEffectiveShift` 시그니처는 그대로 둬서 기존 테스트가 영향받지 않는다.
- 이유: 달력·날짜 화면·요약이 서로 다른 날짜 규칙을 쓰는 불일치를 구조적으로 막는다(명세 "화면 간 일치").

### 3. 이력 갱신 규칙
`applyPatternChange`:
1. 현재 패턴이 없으면(첫 등록·초기화 후) → `{ current: next, history: [] }`.
2. 범위 "전체 기간" → `{ current: next, history: [] }`(지금 동작).
3. 범위 "오늘부터":
   - `effective = resolvePattern(today, timeline)`. `isSameSchedule(effective, next)`면 변경 없음 → 이력을 늘리지 않고 현재 패턴 객체만 새 값으로 유지한다.
   - 아니면 `until > today`인 항목을 버린다(기기 날짜가 과거로 바뀐 경우 날짜순 유지). 남은 마지막 항목의 `until === today`이면(오늘 시작된 패턴을 다시 바꾸는 경우) 현재 패턴만 `next`로 교체한다. 그렇지 않으면 `{ until: today, pattern: effective }`를 이력 끝에 추가하고 현재 패턴을 `next`로 교체한다.
   - 이력이 50개를 넘으면 가장 오래된 항목을 버린다(그 기간은 다음으로 오래된 패턴으로 계산됨).
- 이유: 빈 기간·중복·역순을 만들지 않는다. `effective`를 쓰므로 날짜가 과거로 돌아간 드문 경우에도 오늘의 실제 패턴이 이력에 보존된다.

### 4. 적용 범위 선택은 설정 화면 안의 인라인 라디오로 한다
편집 내용이 저장된 패턴과 다를 때(`isDraftDirty`)만 [저장] 위에 "적용 범위" 두 항목을 보인다(기본: 오늘부터). `onSave(pattern, scope)`로 넘기고 `App.savePattern`이 `applyPatternChange` 결과를 저장한다.
- 이유: 바텀시트·다이얼로그를 쓰면 오버레이 뒤로가기 규칙과 얽히고 출시 가이드의 "행동 강제 유도" 판단 소지가 생긴다. 인라인이면 기존 변경 폐기 확인 규칙만 적용된다. 기본값이 "오늘부터"라 오입력 수정은 한 번 더 선택이 필요하지만, 이는 사용자가 정한 방향이다.
- 대안: 저장 시 확인 창 — 위 이유로 거부. 항상 오늘부터 적용 — 오입력을 고칠 방법이 초기화뿐이라 거부.

### 5. 이력 목록은 근무 패턴 설정 화면 하단의 읽기 전용 섹션
설정 목록(메뉴)에 항목을 추가하지 않고, 근무 패턴 설정 화면의 "오늘 위치"·"날짜 지정" 아래에 둔다. 항목은 `.shift-<TYPE>` 색 칩과 약어로 근무 순서를 보여 주고(최대 56칸, 줄바꿈), 적용 기간 문구는 "YYYY년 M월 D일부터 (현재)" / "처음부터 YYYY년 M월 D일까지" / "YYYY년 M월 D일부터 YYYY년 M월 D일까지"다. 누를 수 있는 요소로 만들지 않는다.
- 이유: 설정 목록의 4항목·순서 명세와 E2E를 바꾸지 않고 요구("설정에 읽기 전용 목록")를 만족한다.

### 6. 검증과 방어
`scheduleStorage`가 `patternHistory`를 읽을 때 항목 패턴·`until` 유효성, `until` 엄격 증가, 50개 이하를 검사하고 하나라도 어긋나면 손상 데이터로 처리한다(저장값은 보존). 현재 패턴이 비어 있어도 유효한 이력은 허용한다. 쓰기는 항상 `version: 3`이며 이력이 비면 필드를 생략한다. `resetPattern`은 `pattern: null`만 만들고 이력은 유지한다(지운 뒤 재등록하는 흐름 보존). 이력만 있고 현재 패턴이 없는 설정에서 재등록하면 적용 범위를 묻지 않고 새 패턴이 마지막 이력 이후 날짜에 적용된다. 이력까지 지우는 것은 전체 초기화뿐이며 확인 창이 이력 삭제를 경고한다.

## Risks / Trade-offs

- [기본값이 "오늘부터"라, 오입력을 고치려는 사용자가 지난 날짜가 안 바뀌어 당황] → 선택 항목 문구에 "지난 날짜도 새 패턴으로 계산"을 명시하고, 이력 목록으로 현재 상태를 확인할 수 있게 한다. 개별 이력 수정은 이번 범위 밖이므로 필요하면 "전체 기간 적용"으로 되돌린다.
- [이력 상한 50개를 넘으면 가장 오래된 기간의 근무가 조용히 바뀜] → 사실상 도달하기 어렵다(50번 변경). 명세에 규칙을 명시하고 단위 테스트로 고정한다.
- [기기 날짜가 과거로 바뀐 상태의 저장] → 3의 정리 규칙과 테스트로 날짜순을 지킨다.
- [번들 롤백 시 이전 앱은 이력을 무시하고 현재 패턴으로 모든 날짜를 계산] → 이전과 같은 동작이라 데이터 손상은 없다. 롤백 시점 안내가 필요하면 릴리스 노트에 적는다.
- [`startDate` 표현이 달라도 같은 일정] → `isSameSchedule`이 위상으로 비교해 "변경 없음"을 정확히 판정하고 이력 중복을 막는다.
- [`pattern` prop을 `timeline`으로 바꾸는 변경 폭] → 호출 지점이 5곳뿐이고 `getShift` 계열 시그니처를 바꾸지 않아 단위 테스트 영향은 요약 테스트의 입력 형태뿐이다. E2E는 저장 흐름(적용 범위 기본값)이 바뀌므로 재확인한다.

## Migration Plan

- 저장 데이터 마이그레이션 없음. 기존 `version: 1·2·3` 데이터는 이전과 같이 복원되며 이력은 없는 상태다.
- 배포: 기능 브랜치 → 단위·시간대·E2E 통과 → `build:adtest`로 실기기 확인(테스트 광고 ID) → 다른 업데이트와 함께 실제 광고 ID 번들로 한 번에 출시(사용자 계획) → 업데이트 검토는 사용자 지시 시.
- 롤백: 콘솔에서 이전 번들로 되돌린다. 저장 형식이 호환이라 사용자 데이터는 유지된다.

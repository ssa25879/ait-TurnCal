# Design

## Context

동기는 proposal.md 참고. 현재 상태에서 설계에 영향을 주는 사실:

- 달력 화면(`CalendarScreen`)은 `pattern`, `days`(날짜별 세부 내용), `today`, `onSelectDate`를 이미 받는다. 요약에 필요한 입력이 모두 있어 **새 상태·저장소·훅이 필요 없다**.
- 그날 근무 규칙은 `getEffectiveShift(date, pattern, day)`가 단일 출처다. 달력 칸(`Calendar.tsx`)과 날짜 화면이 모두 이것을 쓴다.
- 오늘 날짜는 `useToday()`가 `visibilitychange`로 갱신하고 `App`이 `today`로 내려준다. 자정 갱신이 이미 해결되어 있다.
- 공휴일(`getHolidays`), 시간 표기(`formatTimeRange`), 항목 정렬(`sortEntries`), 날짜 이동(`addDays`), 날짜 검증(`isValidDateString`)이 모두 순수 함수로 있다.
- 달력 아래에는 설정 버튼과 배너 광고가 있고 광고는 화면 가로 전체(`margin-left: calc(50% - 50vw)`)를 쓰며 위쪽 간격 32px 규칙이 있다. 요약은 달력 **위**에 들어가므로 이 규칙에는 영향이 없다.
- 근무 색 클래스 `shift-<TYPE>`와 약어 라벨 `SHIFT_LABELS`가 이미 있다.

## Goals / Non-Goals

**Goals:**
- 달력 화면 진입 즉시 오늘·내일 근무를 한눈에 읽게 한다(달력 칸의 작은 약어를 찾을 필요 없음).
- 달력 칸·날짜 화면과 **같은 근무 판정 규칙**을 쓰고 규칙을 중복 구현하지 않는다.
- 저장 형식·광고·권한을 건드리지 않는다.

**Non-Goals:**
- 모레 이후·주간 요약, 근무 시작 알림, 푸시.
- 현재 시각(진행 중인 근무, 남은 시간) 계산. 요약은 날짜 단위다.
- 요약 표시 on/off 설정. 첫 버전은 항상 표시한다.
- 위젯·홈 화면 노출.
- 근무 유형 사용자 정의(별도 후보).

## Decisions

### 1. 요약 값은 순수 도메인 함수로 만든다 (`src/domain/summary.ts`)
`buildDaySummary(date, pattern, day)`가 `{ date, shift, overridden, holidays, timeRange }`를 돌려주고, `buildTodaySummary(today, pattern, days)`가 `[오늘, 내일]`(내일이 지원 범위 밖이면 오늘만)을 돌려준다. 컴포넌트는 값을 그리기만 한다.
- 이유: 시간대·월말·연말·바뀐 근무·범위 밖 같은 규칙을 DOM 없이 단위 테스트할 수 있다. 달력 칸과 같은 `getEffectiveShift`를 호출하므로 판정이 어긋날 수 없다.
- 대안: 컴포넌트 안에서 계산 → 테스트가 E2E에만 의존하고 규칙이 컴포넌트에 묻혀 거부.

### 2. 시간 줄은 "시간순 첫 항목이 시작 시간을 가진 경우만"
`sortEntries`는 시작 시간이 있는 항목을 앞에 두므로, 정렬 첫 항목에 `start`가 있으면 `formatTimeRange(start, end)`를 쓰고 없으면 시간 줄을 생략한다.
- 이유: 새 정렬·선택 규칙을 만들지 않고 날짜 화면의 목록 순서와 일치시킨다. "그날 근무로 적용"으로 고른 항목과 시간이 다를 수 있으나, 요약은 "그날 가장 이른 일정" 의미로 단순하게 둔다(명세에 그대로 기술).
- 대안: 근무 적용 항목(`getShiftSource`)의 시간만 표시 → 분류 없는 시간 메모가 가려져 사용자 기대와 어긋날 수 있어 거부.

### 3. 배치: 월 이동줄 위, 카드 2개 가로 배치
`CalendarScreen`에서 `schedule-header`·알림 문구 아래, `month-nav` 위에 `TodaySummary`를 넣는다. 카드 두 개는 같은 너비로 한 줄에 놓고, 좁은 화면(360px)에서도 한 줄을 유지하되 글자가 넘치면 줄바꿈한다. 카드는 버튼(`button`)이다.
- 이유: 첫 화면 최상단이 시선이 가장 먼저 닿는 곳이고, 달력 아래에는 광고·설정이 있어 광고 간격 규칙과 충돌하지 않는다. 카드 높이를 낮게(약 72~88px) 유지해 달력이 한 화면에서 크게 밀려나지 않게 한다.
- 대안: ① 달력 아래 배치 → 스크롤이 필요하고 광고 간격 규칙과 얽힘. ② 한 카드에 오늘·내일 세로 나열 → 높이가 커져 달력이 더 밀림. ③ 달력 위 고정(sticky) → 안전 영역·내비게이션 바와 간섭 위험이라 거부.

### 4. 갱신은 파생 렌더링으로 해결한다
요약은 props(`today`, `days`, `pattern`)에서 매 렌더 계산하는 파생 값이다. 자정 갱신(`useToday`), 세부 내용·패턴 저장 후 복귀는 상태가 바뀌면 자동으로 다시 그려지므로 별도 구독·타이머를 두지 않는다.
- 이유: 상태를 하나 더 두면 불일치(오늘 강조는 새 날짜인데 요약은 이전 날짜) 위험이 생긴다. 계산량이 칸 2개 분량이라 메모이제이션도 불필요.

### 5. 스타일은 기존 토큰만 쓴다
근무 색은 기존 `shift-<TYPE>`, 글자색·테두리는 `--color-*` 토큰, 강조는 테마 `--color-primary`. 토스 브랜드 색(`#3182F6`·`#0064FF` 계열)과 `Toss Product Sans`는 쓰지 않고, 다크 모드 규칙도 추가하지 않는다. 글자 크기는 11px 이상, 카드 누름 영역은 44px 이상이다.
- "오늘" 카드는 테마 약한 배경(`--color-primary-weak`)으로 "내일" 카드와 구별한다(색만이 아니라 "오늘"/"내일" 글자 라벨도 있다).

### 6. 지원 범위 끝은 카드를 생략해 처리한다
`addDays(today, 1)`이 `isValidDateString`을 통과하지 못하면(2101-01-01 이후) 내일 항목을 만들지 않는다. 오늘은 `useToday`가 항상 유효한 로컬 날짜를 주므로 별도 처리하지 않는다.
- 이유: 오류·빈 카드 대신 조용히 생략하는 쪽이 사용자에게 덜 이상하고, 실제로는 도달하기 어려운 경계다.

## Risks / Trade-offs

- [달력이 아래로 밀려 한 화면에 격자 전체가 안 보일 수 있음] → 카드 높이를 낮게 유지하고 360×640에서 E2E로 격자·설정 버튼 접근을 확인한다. 화면은 이미 스크롤 가능(배너 때문)이라 접근성은 유지된다.
- [요약 시간(가장 이른 일정)과 "그날 근무로 적용"한 항목의 시간이 달라 혼란] → 명세에 규칙을 명시하고 날짜 화면에서 같은 순서를 보여 준다. 사용자 반응을 보고 규칙을 바꾼다(스키마 변경 없이 가능).
- [요약 카드와 달력 오늘 칸의 정보 중복] → 의도된 중복이다(요약은 읽기 쉬운 크기, 달력은 한 달 개관).
- [E2E 기존 선택자·좌표가 달력 위치에 의존] → 달력 위치를 가정한 검사(광고 간격·위치)를 구현 후 전부 다시 실행한다.
- [출시 가이드 위반] → 카드에 광고·자사 유도·진입 바텀시트가 없고, 새 권한·네트워크가 없다. 업데이트 검토 전 가이드 대조표를 다시 확인한다.

## Migration Plan

- 저장 데이터·설정 변경이 없어 마이그레이션이 없다. 기존 사용자 데이터는 그대로 호환된다.
- 배포: 기능 브랜치 구현 → `npm test`·`test:tz`·E2E 통과 → `build:adtest`로 실기기 확인(테스트 광고 ID) → 실제 광고 ID 빌드 → 업로드 → 업데이트 검토 요청(사용자 지시 시).
- 롤백: 문제가 생기면 콘솔의 이전 번들(`20261013-8`)로 `bundle_rollback`. 저장 형식이 같아 데이터 영향 없음.

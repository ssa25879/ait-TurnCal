# ICS 저장 캘린더 실기기 실험 (E1~E4)

근거: [ICS_TARGET_CALENDAR_ANALYSIS.md](../ICS_TARGET_CALENDAR_ANALYSIS.md) 4절. 결과는 `openspec/changes/improve-release-quality-and-analytics/verification.md`의 C02·C03에 반영한다.

## 파일

모든 파일은 앱의 `buildIcs`(`src/domain/monthExport.ts`)로 생성했다. 파일 형식은 앱 산출과 같고, 실험 구분을 위해 날짜·근무 이름·캘린더 이름만 바꿨다. 링크는 넣지 않았고 알림은 켜짐(전날 21:00, `TRIGGER:-PT3H`)이다.

`.ics` 파일은 저장소에 넣지 않았다. 실험에 쓴 파일은 사용자 구글 드라이브 `ait-turncal` 폴더에 있다.

| 파일 | 일정 날짜 | 근무 이름(SUMMARY) | `X-WR-CALNAME` | UID |
|---|---|---|---|---|
| `E1-basic-2027-01.ics` | 2027-01-05~07 | `E1 주간/오후/야간` | `턴캘 실험 E1 · 2027년 1월` | `turncal-2027010x@ait-turncal` |
| `E2a-calname-google-2027-02.ics` | 2027-02-05~07 | `E2a …` | `구글 캘린더` | 2월 날짜 UID |
| `E2b-calname-samsung-2027-03.ics` | 2027-03-05~07 | `E2b …` | `삼성 캘린더` | 3월 날짜 UID |
| `E3-same-uid-as-E1-2027-01.ics` | 2027-01-05~07 | `E3 …` | E1과 같음 | **E1과 같음**, DTSTAMP만 1시간 늦음 |
| `E4-account-active-2027-04.ics` | 2027-04-05~07 | `E4 …` | `턴캘 실험 E4 · 2027년 4월` | 4월 날짜 UID |

실험 월(2027년 1~4월)은 기존에 가져온 근무표와 UID가 겹치지 않도록 골랐다.

## 순서

1. 시작 전: 2027년 1~4월에 일정이 없는지 확인한다. 구글 계정 캘린더 동기화 상태를 적는다.
2. E1 → E2a → E2b → E3 → (구글 계정 캘린더 활성화) → E4 순서로 가져온다. E3는 반드시 E1 다음에 가져온다.
3. 파일마다 열 때 나타나는 앱 선택 목록과 가져오기 화면(대상 캘린더 선택 가능 여부)을 캡처한다.
4. 실험 후 2027년 1~4월 일정과 가져오기로 생긴 캘린더를 삭제할지는 결과 기록 뒤 판단한다.

- 같은 UID를 다시 가져오면 저장이 거부된다(E3). C02·C03에서 갱신이 안 된 원인과 맞아떨어진다.

## 2차 실험: 알림 변경 (E5·E6)

| 파일 | 내용 | 확인 내용 |
|---|---|---|
| `E5-alarm-1900-same-uid-2027-01.ics` | E1과 같은 UID·근무 이름, 알림만 전날 21:00 → **19:00**(`TRIGGER:-PT5H`) | 저장되는지, 1월 5~7일 알림이 19:00으로 바뀌는지 |
| `E6-alarm-1900-sequence1-2027-01.ics` | E5 + `SEQUENCE:1`(수정 차수 증가, 현재 앱에는 없는 속성) | E5가 거부될 때 수정 차수를 올리면 갱신되는지 |

순서: E5를 먼저 가져온다. E5가 거부될 때만 E6를 가져온다. E5가 저장되면 그 상태를 기록하고, E6는 가져오지 않는다.

| 실험 | 저장 여부·메시지 | 1월 5~7일 일정 수 | 알림 값 | 비고 |
|---|---|---|---|---|
| E5 | 갱신·추가 안 됨 (사용자 보고) | | | |
| E6 | 갱신·추가 안 됨 (사용자 보고) | | | |

정리: 이 기기에서는 이미 가져온 UID가 들어 있는 파일로 기존 일정을 고칠 수 없다. 근무 이름(E3)·알림(E5)을 바꿔도, 수정 차수를 올려도(E6) 마찬가지다. 앱의 "같은 UID라 다시 가져오면 갱신된다"는 전제는 이 기기에서 성립하지 않는다.

## 3차 실험: 부분 중복·삭제 후 재가져오기 (E7·E8)

| 실험 | 파일 | 조건 | 확인 내용 |
|---|---|---|---|
| E7 | `E7-partial-overlap-2027-01.ics` | 1월 5~9일 5건. 5~7일은 E1과 같은 UID, 8·9일은 새 UID. 근무 이름 `E7 …` | 파일 전체가 거부되는지, 8·9일만 추가되는지 |
| E8 | `E5-alarm-1900-same-uid-2027-01.ics` 재사용 | 캘린더에서 1월 5~7일 `E1 …` 일정을 직접 지운 뒤 E5를 가져옴 | 지운 UID를 다시 가져올 수 있는지, 알림이 19:00인지 |

순서: E7 → E8. 실제 근무표와 같은 상황(달 중간에 근무 추가, 지우고 다시 가져오기)을 확인한다.

| 실험 | 저장 여부·메시지 | 1월 5~9일 일정 | 알림 값 | 비고 |
|---|---|---|---|---|
| E7 | 저장됨(일부) | `E1 주간`·`E1 오후`·`E1 야간`·`E7 주간`·`E7 오후` | 미기록 | 5~7일은 기존 유지, 8·9일만 추가 |
| E8 | 저장 성공 | 5~7일 E5 내용 | 미기록(19:00 여부 확인 필요) | 하나씩 직접 지운 뒤 가져옴 |

정리:
- 같은 UID가 있는 일정은 건너뛰고, 새 UID만 추가된다. 파일 전체가 거부되지는 않는다(E7).
- 기존 일정을 지우면 같은 UID로 다시 가져올 수 있다(E8).
- 따라서 근무가 바뀐 달은 "그 달 일정을 지운 뒤 다시 가져오기"로 반영할 수 있다. 지우지 않고 다시 가져오면 바뀐 날은 이전 근무로 남고 새로 생긴 날만 추가돼 달력이 섞인다.

## 판정 기준

- E2a·E2b의 저장 위치가 E1과 같으면 `X-WR-CALNAME`은 대상 지정에 쓰이지 않는다고 본다.
- E3 뒤 1월 5~7일에 `E3 …`만 3건이면 갱신, `E1`·`E3`가 함께 6건이면 중복 생성, `E1`만 3건이면 무시로 기록한다.
- E4에서 선택 목록이나 가져오기 화면에 계정 캘린더가 추가되면 대상은 기기 화면에서 고르는 것으로 기록한다.

## 4차 실험: 삼성·구글 캘린더 대상 (S·G)

1~3차는 모두 `내 캘린더(내 폰)` 기준이다(E2a·E2b 제외). 같은 확인을 삼성 계정 캘린더와 구글 캘린더에서 반복한다. 기기에 저장된 일정과 UID가 겹치지 않도록 삼성은 2027년 5월, 구글은 2027년 6월을 쓴다.

| 파일 | 내용 | 대응 실험 |
|---|---|---|
| `S1-samsung-basic-2027-05.ics` / `G1-google-basic-2027-06.ics` | 5~7일 3건, 이름 `S1 …`/`G1 …`, 알림 21:00 | E1 |
| `S2-…-alarm-1900-same-uid-…` / `G2-…` | T1과 같은 UID·이름, 알림만 19:00 | E5 |
| `S3-…-partial-overlap-…` / `G3-…` | 5~9일 5건(5~7일 같은 UID), 이름 `S3 …`/`G3 …` | E7 |

가져오기 화면에서 저장 캘린더를 고를 수 없으므로, 저장 위치는 캘린더 앱의 기본 캘린더 설정을 따르는 것으로 가정한다(E2a·E2b가 Google로 저장된 결과 근거, 미확정).

순서(삼성 → 구글 각각):
1. 캘린더 앱 설정에서 새 일정의 기본 캘린더를 대상(삼성 계정 / 구글 계정)으로 바꾼다. 메뉴 이름은 기기에서 확인한다. 바꿀 수 없으면 그 사실을 기록하고, 가져온 일정이 어느 캘린더에 들어갔는지만 기록한다.
2. T1을 가져오고, 일정 상세에서 저장된 캘린더 이름을 확인한다. 대상과 다르면 여기서 멈추고 기록한다.
3. T2를 가져온다 → 알림이 19:00으로 바뀌는지.
4. T3를 가져온다 → 8·9일만 추가되는지.
5. 5~7일 일정을 지우고 T2를 다시 가져온다 → 저장되는지, 알림 19:00인지(E8 대응). 구글은 지운 뒤 동기화가 끝날 때까지 기다렸다가 가져온다.

| 실험 | 저장된 캘린더 | T2 갱신 | T3 결과 | 삭제 후 T2 | 알림 값 | 비고 |
|---|---|---|---|---|---|---|
| 삼성(S) | | | | | | |
| 구글(G) | | | | | | 웹 calendar.google.com에서도 같은 결과인지(선택) |

### 4차 결과 (2026-10-27, 사용자 보고)

- S1~S3·G1~G3 모두 `내 캘린더(내 폰)`에 저장됐다. 기본 캘린더 설정으로 저장 위치를 바꾸는 방법은 아직 확인하지 못했다.
- E2a·E2b(캘린더 이름 `구글 캘린더`·`삼성 캘린더`)만 Google로 저장됐다는 앞선 보고와 맞지 않는다. 파일의 캘린더 이름으로 새 로컬 캘린더가 생겼는데, 그 이름 때문에 Google로 보였을 가능성이 있다(가정). 캘린더 관리 목록에서 확인이 필요하다.

## 5차 실험: 1·2월 재사용 + 대상 캘린더 이름 (S·G 재생성)

E 실험 일정을 지웠으므로(사용자 확인) 2027년 1~3월을 다시 쓴다. 5·6월 S·G 파일은 이 파일로 대체한다.

| 파일 | 달 | `X-WR-CALNAME` |
|---|---|---|
| `S1~S3-samsung-…-2027-01.ics` | 2027년 1월 | `삼성 캘린더` |
| `G1~G3-google-…-2027-02.ics` | 2027년 2월 | `구글 캘린더` |

캘린더 이름을 대상 이름으로 넣은 이유: 이름이 `턴캘 실험 …`인 파일(E1·S·G)은 모두 내 폰에 저장됐고, 이름이 `구글 캘린더`·`삼성 캘린더`인 E2a·E2b만 Google로 보고됐다. 이름이 저장 위치에 영향을 주는지 다시 확인한다. 3월은 예비로 비워 둔다.

순서와 기록표는 4차 실험과 같다. 가져오기 전후로 캘린더 관리 목록에 새 캘린더가 생기는지도 적는다.

### 5차 결과 (2026-10-27, 사용자 보고)

S·G 파일도 모두 `내 폰`에 저장됐다. 파일 안의 캘린더 이름(`삼성 캘린더`·`구글 캘린더`)은 저장 위치를 바꾸지 못한다. 그래서 가져온 일정을 사용자가 직접 Google·삼성 캘린더로 옮긴 뒤 같은 순서로 확인했다.

| 단계 | 결과 |
|---|---|
| 1. 처음 가져오기 → 직접 Google/삼성으로 이동 | 정상. 일정 하나의 캘린더를 바꾸면 같이 가져온 나머지도 한 번에 바뀜 |
| 2. 같은 UID·알림 19:00 | 반영·저장 안 됨 |
| 3. 부분 중복(5~9일) | 기존 일정 덮어쓰기 안 됨, 8·9일은 추가됨 |
| 4. 5~7일 삭제 후 2번 다시 가져오기 | 저장됨, 알림 19:00. 각각 Google/삼성 캘린더에 저장됨 |

4단계에서 일정이 `내 폰`이 아닌 직전에 옮긴 캘린더에 저장됐다. 사용자 판단으로는 마지막에 저장(이동)한 캘린더가 기본값처럼 적용되는 것으로 보인다(추정). E2a·E2b가 Google로 저장된 것도 이 때문일 수 있다.

## 종합 판단 (내 폰·Google·삼성 공통)

- 파일 내용이나 가져오기 화면으로는 저장 캘린더를 정할 수 없다. 처음에는 `내 폰`에 저장되고, 사용자가 일정을 다른 캘린더로 옮기면 그 뒤 가져오기는 그 캘린더에 저장되는 것으로 보인다(추정, 기기 상태에 따라 다름).
- 이미 있는 UID는 다시 가져와도 바뀌지 않는다(근무 이름·알림·`SEQUENCE` 모두). 새 날짜만 추가된다.
- 기존 일정을 지우면 같은 UID로 다시 가져올 수 있다.
- 따라서 근무를 바꾼 뒤 반영하려면 "그 달 턴캘 일정을 지운 뒤 다시 가져오기"가 필요하다. 다시 가져온 일정은 직전에 쓴 캘린더에 들어가는 것으로 보이므로, 저장 위치는 가져온 뒤 확인하도록 안내한다.

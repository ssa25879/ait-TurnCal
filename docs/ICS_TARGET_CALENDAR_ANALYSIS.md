# ICS 가져오기 저장 캘린더 지정 가능성 분석

작성일: 2026-10-27
대상: 캘린더 파일 내보내기(`src/domain/monthExport.ts`)가 만든 `.ics`를 Galaxy S26 Ultra에서 가져올 때 저장 캘린더를 파일이 지정할 수 있는지
상태: **실기기 검증 완료**(2026-10-27, Galaxy S26 Ultra 기본 캘린더 앱, 사용자 수행). 결과는 7절, 사례별 기록은 [ics-experiments/README.md](ics-experiments/README.md)

## 1. 확인한 사실

### 1.1 기기에서 관찰한 동작 (사용자 확인)

- ICS 파일을 실행하면 선택 목록에 **“캘린더” 앱만** 나타나고, 다른 캘린더 앱은 나타나지 않는다.
- 내장 “캘린더” 앱 안에는 `내 폰 저장`, `구글 캘린더`, `삼성 캘린더`, `리마인더` 네 캘린더가 함께 묶여 있다.
- ICS 파일은 `내 폰 저장`에 들어가는 방식으로 동작한다고 확인했다.
- 같은 파일 재가져오기와 근무 변경 뒤 재가져오기에서 일정이 갱신되지 않았고, 덮어쓰기·저장 버튼이 나타나지 않았다 (C02·C03, 차이 있음).

### 1.2 현재 앱이 파일에 쓰는 속성

`src/domain/monthExport.ts`에서 생성하는 VCALENDAR 헤더는 다음과 같다.

| 속성 | 값 | 비고 |
|---|---|---|
| `PRODID` | `-//TurnCal//KO` | 제작자 식별 |
| `X-WR-CALNAME` | 월 제목(예: `병동 3교대 2026년 10월`) | 비표준 속성 |
| `UID` | `turncal-YYYYMMDD@ait-turncal` | 날짜별 고정 |
| `VALARM` | 근무 전날 알림 | 파일에 포함 |

`X-WR-CALNAME`은 앱이 파일 안에 넣은 “캘린더 이름” 힌트다. 현재 코드는 이 값을 캘린더 선택에 쓰지 않는 상태로 보인다.

### 1.3 표준 확인

- ICS 형식(RFC 5545)에는 “이 일정을 어느 캘린더 계정·앱에 저장하라”는 표준 속성이 없다. 저장 대상은 가져오기를 수행하는 앱과 사용자의 선택이 정한다.
- `X-WR-CALNAME`은 표준이 아닌 확장 속성이다. 일부 앱은 캘린더 이름 표시에 쓰지만, 가져오기 대상을 정하는 데 쓴다고 보장되지 않는다.
- 외부 검색 결과(2026-10-27 확인): Samsung 커뮤니티 글에서 ICS를 열면 **새 로컬 캘린더가 생성되고**, 기존 캘린더를 지정하는 방법을 찾지 못한다는 보고가 있다. 다만 공식 문서로 확인하지는 못했다.

## 2. 판단

| 질문 | 판단 | 근거 |
|---|---|---|
| ICS 파일 안에 저장 캘린더를 표준으로 지정할 수 있는가 | **불가능**으로 본다 | RFC 5545에 해당 속성이 없음 |
| `X-WR-CALNAME`으로 `내 폰 저장` 등 대상을 고를 수 있는가 | **보장되지 않음**, 검증 필요 | 비표준 속성, 기기 가져오기 UI가 이를 대상 선택에 쓰는지 확인 불가 |
| 현재 기기에서 “캘린더” 앱만 보이는 현상이 파일 때문인가 | **파일 속성으로 확정할 수 없음** | 대상 목록은 OS의 파일 처리 경로가 정한다. 앱이 바꿀 수 없는 영역일 가능성이 높음 |
| 재가져오기 갱신이 안 되는 원인이 파일 속성인가 | **미확정** | 같은 UID를 쓰더라도 로컬 `내 폰 저장`의 가져오기 정책이 갱신을 보장하지 않을 수 있음 |

결론: **ICS 파일만으로 `내 폰 저장`·`구글 캘린더`·`삼성 캘린더`를 고르게 하는 것은 표준상 보장되지 않는다.** 현재 기기의 “캘린더” 앱 하나만 보이는 동작은 파일이 아니라 OS·앱의 가져오기 경로가 정하는 것으로 보는 것이 합리적이다.

## 3. 검증이 필요한 이유

- 사용자 요청과 설계 문서(`design.md`)는 “어떤 캘린더에 들어갔는지”를 사례마다 기록하도록 하고 있다. 대상이 파일로 정해지는지 모르면 C02·C03의 원인을 가릴 수 없다.
- 현재 결과는 “갱신 안 됨 + 덮어쓰기 버튼 없음”뿐이다. 중복 생성인지, 무시인지, 새 로컬 캘린더인지 기록되지 않았다.
- 대상 지정이 가능하다면 앱 안내 문구와 내보내기 설명을 그에 맞게 바꿔야 한다. 불가능하다면 안내 문구는 “가져올 캘린더는 기기 선택 화면에서 고른다”로 맞춰야 한다.

## 4. 검증 계획 (실기기, 미실행)

테스트 파일을 여러 개 만들어 같은 기기에서 가져온다. 파일마다 UID와 제목을 달리해 중복과 대상 캘린더를 구분한다.

| 실험 | 파일 조건 | 확인 내용 |
|---|---|---|
| E1 기본 파일 | 현재 앱 산출 그대로 | 가져온 캘린더 이름, 일정 수, 생성 위치 |
| E2 캘린더 이름 힌트 | `X-WR-CALNAME`을 `구글 캘린더` 또는 `삼성 캘린더`로 바꾼 파일 | 선택 목록·저장 위치가 바뀌는지 |
| E3 UID 재사용 | E1과 같은 UID로 제목만 바꾼 파일을 다시 가져옴 | 갱신·중복·거부 중 무엇인지 |
| E4 계정 캘린더 존재 시 | 구글 계정 캘린더가 활성인 상태에서 E1 | 대상 목록에 계정 캘린더가 추가로 나타나는지 |

기록 항목: 기기, OS, 캘린더 앱 버전, 가져온 캘린더 이름, 일정 수, 중복 여부, UID 유지 여부, 선택 목록의 항목.

## 5. 권장 조치

1. 실험 E1~E4를 수행해 결과를 `verification.md`의 C02·C03 행에 반영한다.
2. 파일로 대상을 지정할 수 없다는 결과가 나오면 설명 문구를 “가져올 캘린더는 기기 선택 화면에서 고른다”로 한정한다. 실제 대상은 앱이 보장하지 않는다고 적는다.
3. 파일 생성 로직(UID·VALARM·`X-WR-CALNAME`)은 검증 전에는 바꾸지 않는다. 바꾸면 C01·C02 회귀를 다시 확인해야 한다.
4. 외부 캘린더 계정에 직접 쓰는 기능(동기화·자동 삭제)은 이 분석 범위 밖이며 추가하지 않는다.

## 7. 실기기 검증 결과 (2026-10-27)

4절 계획(E1~E4)에 알림 변경(E5·E6), 부분 중복·삭제 후 재가져오기(E7·E8), 구글·삼성 캘린더 반복(S·G)을 더해 수행했다. 2절 판단을 다음과 같이 확정한다.

| 질문 | 결과 | 근거 |
|---|---|---|
| 파일로 저장 캘린더를 지정할 수 있는가 | **불가능.** `X-WR-CALNAME`을 `구글 캘린더`·`삼성 캘린더`로 바꿔도 저장 위치가 바뀌지 않음 | E2a·E2b, S·G |
| 가져오기 화면에서 고를 수 있는가 | **불가능.** 선택 화면이 나타나지 않음 | E1·E4 |
| 저장 위치는 무엇이 정하는가 | 처음엔 `내 폰 저장`. 가져온 일정을 다른 캘린더로 옮긴 뒤에는 그 캘린더에 저장됨(추정: 마지막 사용 캘린더가 기본값처럼 적용) | S·G 4단계, E2 |
| 같은 UID 재가져오기로 갱신되는가 | **안 됨.** 근무 이름·알림을 바꾸거나 `SEQUENCE:1`을 넣어도 마찬가지 | E3·E5·E6, S2·G2 |
| 기존·새 UID가 섞인 파일 | 기존 일정은 그대로, 새 날짜만 추가 | E7, S3·G3 |
| 지운 뒤 재가져오기 | 저장되고 바뀐 알림이 반영됨 | E8, S·G 4단계 |

`내 폰 저장`·구글·삼성 캘린더 모두 결과가 같았다. 구글·삼성은 가져온 일정을 사용자가 직접 옮겨 확인했다. 일정 하나의 캘린더를 바꾸면 같이 가져온 일정이 함께 옮겨졌다.

**조치(반영됨):**
- 파일 생성 규칙(날짜별 고정 UID·VALARM·`X-WR-CALNAME`)은 유지한다. 같은 파일을 두 번 가져와도 중복이 생기지 않는다. `SEQUENCE`는 효과가 없어 넣지 않는다.
- 내보내기 시트에 "이미 가져온 달은 그 달 일정을 지운 뒤 가져와야 바뀌어요. 저장된 캘린더는 가져온 뒤 확인해 주세요."를 추가했다.
- 알림 설정 화면의 재가져오기 안내를 "다시 가져와도 기존 일정은 그대로라서, 그 달 일정을 지운 뒤 가져와 주세요."로 바꿨다.
- `verification.md`의 C02·C03을 **차이 있음(앱 한계, 안내로 대응)**으로 확정했다.

**남은 한계:** 기기 한 대(Galaxy S26 Ultra)의 기본 캘린더 앱에서만 확인했다. OS·앱 버전, iOS, 다른 캘린더 앱의 동작은 확인하지 않았다.
